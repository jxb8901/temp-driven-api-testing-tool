## Job workspace

### Detach and restore a Job console

From **Live Output**, **Events**, or the Job detail header, choose **Open floating console**. The non-modal console stays mounted above the Studio shell while you move between Explorer, Configuration, Load testing, Jobs, and Settings. It shows the Job ID, RUN/DEBUG/LOAD type, status, SSE state, searchable Live Output and structured Events, pause/resume, copy, maximize/restore, and close controls. On desktop, drag the **Move console** handle or use its arrow keys; use the corner handle or its arrow keys to resize. The panel is clamped to the viewport. On smaller screens it becomes a full-screen sheet.

There is one floating console per Studio tab. Opening a different Job asks you to confirm **Switch Job**. **Minimize** keeps a bottom console chip and one bounded per-tab SSE subscription so status and new events remain current without rendering hidden event rows; the selected view, searches, filters, and scroll preferences remain in memory. **Close** releases that subscription. None of these controls cancels or stops the Job.

**Open full Job Details in a new tab** opens `#/jobs/{encodedJobId}?standalone=1&tab=live` (or `events`) with Overview, Live Output, Events, Results, Artifacts and Metrics. Tab switching updates the URL while keeping the Job fixed. Old `#/jobs/{jobId}/console?view=live|events` bookmarks adapt to the full Details workspace. Same-origin `target="_blank" rel="noopener noreferrer"` links support `/att/ui/`, refresh and browser navigation. One Job stream is shared within each tab; floating/docked/minimized consoles keep their existing behavior. Inaccessible Jobs show safe unavailable or sign-in messages.

The browser ingests events immediately into a 500-entry bounded buffer and publishes ordinary display snapshots at a fixed 100 ms cadence. It pauses those display publications while the document is hidden, then publishes the current bounded snapshot when the document becomes visible. Terminal `result` events, terminal `status` events, cancellation-request status, and connection error transitions publish immediately. The timer and native `EventSource` are released when the last consumer closes.

The Events list renders only the rows near its scroll position (plus spacers that keep the scrollbar and list positions exact), keeps event payloads collapsed until expanded, and searches the full 500-entry window rather than only the rendered rows.

LOAD Overview, Results and basic Metrics use the bounded `att-load-terminal-result/v1` projection. It shows execution outcome, performance verdict, aggregate counts and the primary runtime/preparation/validation cause immediately. Overview reads the compact `/jobs/{jobId}/artifacts/status` summary; it does not enumerate the artifact index or fetch report content. It polls only while publication is PENDING or ARCHIVING, stops when the tab changes or the page is hidden, and labels a result-supplied report path as unverified until the Server confirms the archive summary. A report link appears only for a verified approved path. The Overview keeps archive state separate from job result state and shows approved-file counts, omission counts and safe omission categories; older archive formats without categories say that the reason is unavailable. Aggregate and workload threshold counts remain separate, as do execution status and performance verdict.

Results and Metrics check archive state through the authorized artifact index only after those tabs are opened. Opening Results loads the authorized `load-summary.json` preview, including bounded evidence records and workload summaries with links to workload sidecars. Opening Metrics loads `load-summary.json` and its referenced metric-series sidecars through the authorized artifact text route; detailed tables and charts are rendered only after the report is ready. The archived detailed report uses `att-load-summary/v1.3`; its large series live in versioned relative files under `details/v1/`. The Artifacts tab loads its index only when opened. For a loaded report, charts use returned buckets (up to 4,096), while the accessible bucket table shows 100 rows per page with Previous and Next controls and a `Showing rows` status. Bucket coverage identifies the 4,096-entry rolling one-second window and the separate `LoadWindowMetrics` bin width and coverage. The isolated report preview retains a restrictive iframe sandbox and allows only reviewed, hash-matched report scripts; report links are opened through the authenticated parent UI.

When a scheduler returns a LOAD result but resource cleanup fails, ATT keeps the completed metrics and publishes the report with a bounded `TEARDOWN` diagnostic. Cleanup is secondary to an existing execution failure. A cleanup failure changes the execution outcome to ERROR while the performance verdict remains independent; cancellation with failed cleanup is also reported as ERROR and retains partial metrics. ATT does not publish a report when no scheduler result exists.

The Server Journal Event ID is the append-order key, and IDs remain monotonic within each Job across Server restarts, journal trimming, and compaction. The UI shows events in Server append order without timestamp sorting. A numeric ID that is not greater than the last displayed ID is ignored, counted as a duplicate or stale out-of-order replay, and never re-sorted into the list. A forward gap is allowed and counted only for diagnostics. Non-numeric IDs use a bounded recent-ID index for de-duplication. Native `EventSource` reconnects with `Last-Event-ID`, and overlap replays cannot reappear after they leave the visible window or after **Clear view**. The non-live **Stream diagnostics** line reports ignored duplicates, out-of-order replays, and ID gaps when any count is non-zero.

These limits describe different layers. The browser shows only its latest 500 accepted events and does not claim to hold the complete Job history. The Server journal controls what can be replayed and reports when earlier journal history has been truncated. The per-entry limits tracked by #265 shorten text or payload fields before or during publication; the browser does not reconstruct or reformat that protocol data.

The Advanced Load route uses typed controls for duration units, Virtual Users, Arrival Rate, maximum concurrency, and think time. Target sidecar defaults use typed scalar controls for `inputs`, `vars`, and Tool `arguments`; nested values remain in Advanced JSON. Model-specific constraints are reflected in the form, while the Server remains authoritative for validation, policy limits, draft expiry, package revision, and execution. The UI reviews and submits the same Server-issued draft after confirmation, and only offers preview copy/export when the response is not redacted.

Jobs uses Server filtering, target sorting/grouping and real pagination across matching history. Target links open the exact Job Details; Package/Environment, copyable short Job ID, Schedule principal and Created/Started/Finished/elapsed accompany each row. Recent Jobs remains newest first. Rows per page supports 25/50/100 (default 100, saved locally). Row Pin/Delete icons apply immediately. The two footer menus set pin/unpin or mark/unmark for every Job on this page, including collapsed groups; per-ID outcomes explain partial changes. A deletion mark stays reversible before background claim after at least 30 seconds. Pinned, active, busy and quarantined Jobs remain protected. Job Details retains Overview, Live Output, Events, Results, Artifacts and Metrics; cancellation still requires confirmation.

The Explorer is a React and TypeScript single-page UI built with Vite during the `att-web` Maven resource phase. Maven copies the generated static assets into `META-INF/resources/ui/`; the Server WAR packages those assets for Tomcat. Node.js is a build-time tool only. The deployed UI calls the same-origin public REST API and does not require a separate Node process or frontend service.

### Jobs filters and replay review

Jobs keeps Principal, Package, Type, Status and Target search in a compact toolbar. **More filters** reveals Created from/to, Deletion state and Pin state; active values remain visible when collapsed. Target search includes every retained canonical target or selected Case ID, including targets beyond the first 32 preview entries, before Server pagination. Legacy Jobs without retained target metadata remain searchable by Job ID. After an upgrade, historical target indexing resumes in background batches. Browsing without a search remains available; until indexing finishes, substring Target or Job ID searches return a retryable 503 (`ATT-SERVER-TARGET-SEARCH-PENDING`) with no partial results. Use **Refresh jobs** to retry. For an exact, case-sensitive lookup, enter `job:` followed by the complete Job ID (for example, `job:J0123456789ABCDEF`); this primary-key lookup remains available during indexing and retains every other filter, count and pagination rule. Malformed historical snapshots/identities are isolated per Job, marked processed with a safe fallback or empty target set, and audited without private metadata; they do not block indexing forever. Group by Target always displays Target A–Z, with Jobs newest first inside each group; returning to Recent Jobs restores its selected sort.

From Jobs List, Job Details or LOAD History, **Rerun with same settings** opens a review with **Use current Package** (default) and **Require original revision (strict)**. Current mode reuses the prior safe parameters but validates them against the current Package and configuration. Strict mode blocks a changed revision and offers **Review with current Package**. Schedule package-change policy does not control manual Rerun.

**Configure & Rerun** creates a short-lived authorized server draft and opens the standard RUN/LOAD editor with supported retained values prefilled. The URL contains only an opaque `draftRef`; the definition is fetched with an authorized, `private, no-store` request. After edits, **Validate → Review changes → Run** shows the before/after definition, current revision, and LOAD timing/rate details. Back/Cancel leaves the Job, report, Schedule and package source unchanged. **Schedule / Reschedule…** stays separate and offers new Schedule creation or the authorized originating Schedule; it never starts a Job.
