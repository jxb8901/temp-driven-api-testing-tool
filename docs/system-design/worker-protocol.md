# ATT Worker protocol v1

`att-worker` is the internal process adapter used by ATT Server. Each normal process accepts one JSON request on stdin, invokes one typed `AttService` operation directly, writes JSON Lines records to stdout, and exits. Inspection daemons are read-only and reject execution commands. The opt-in [one-shot prewarm handshake](execution-prewarm.md) precedes the same single execution request and does not permit cross-Job JVM reuse.

## Request

The request is a JSON object. `protocolVersion` must equal `att-worker/v1`; unsupported versions are rejected with a `DIAGNOSTIC` followed by an `INVALID` `RESULT`. Empty, malformed, truncated, or multiple JSON documents are rejected through the same terminal event sequence. `jobId` identifies Worker orchestration events; it is independent of the ATT `executionId` returned inside an operation result. `command` is one of `run`, `debug`, `load`, `validate`, or `snapshot`. `packageRoot` is required and is passed explicitly to the engine, independently of the process working directory.

Common optional fields are `config`, `environment`, `outputDirectory`, and `runId`. Relative config, suite, scenario, and output paths are interpreted by the engine relative to the supplied package root. `target` contains `type` and `id` for Debug or `load` without a scenario. `suites`, `suiteDirectory`, `caseIds`, `tags`, `excludeTags`, and `all` select Run, Validate, or Snapshot input. `load` contains optional policy overrides such as `users`, `arrivalRate`, `duration`, and `maxConcurrent`; `overrides` carries typed input/argument/variable assignments using the same safe value syntax accepted by ATT.

Example:

```json
{
  "protocolVersion": "att-worker/v1",
  "jobId": "J20261006-000123",
  "command": "debug",
  "packageRoot": "/srv/att/packages/payment",
  "environment": "SIT",
  "target": { "type": "flow", "id": "payment.invoke.v1" }
}
```

## Events

Every event is one JSON object followed by a newline. Each event includes `type` and, when known, `jobId`. Stable v1 types are:

| Type | Meaning |
| --- | --- |
| `STATUS` | Worker lifecycle, initially `RUNNING`. |
| `LOG` | A safe, structured execution log message. |
| `PROGRESS` | A machine-readable progress observation. |
| `DIAGNOSTIC` | A structured request, configuration, validation, or runtime problem. |
| `RESULT` | The canonical operation result, status, and process exit code. |

The first implementation emits `STATUS`, zero or more `LOG` / `PROGRESS` events while an operation runs, then `RESULT`; invalid or failed requests may emit `DIAGNOSTIC` before the terminal `RESULT`. Non-LOAD operation results carry `executionId`, `status`, `exitCode`, duration, typed diagnostics, paths, and summary. A Server-mediated LOAD result instead uses the versioned `att-load-terminal-result/v1` projection in `result.summary`; the Engine builds it from bounded metric views without serializing the full CLI result. Its primary runtime/preparation cause and observed failed counts take precedence over transport symptoms. Complete LOAD metrics, bucket series and retained evidence stay in the report artifacts. The direct Engine/CLI result continues to use the full legacy summary contract; its schema definition remains under `schemas/history/`; archived `LoadReportWriter` output uses the additive `att-load-summary/v1.3` schema and `details/v1/` sidecars. A Run result reports the ID generated by the engine when the request omits `runId`. CLI-formatted text is never copied from the Worker process standard streams. Execution events may include two additive fields: `executionEventType` (the original engine event type) and `console` (one plain-text line produced by the shared formatter). LOAD iteration events omit `console` except for the bounded start, periodic progress, rate-limited error, and completion lines. The Server stores that line for Live Output and does not read Worker stdout or stderr as a terminal transcript. Bootstrap parse errors are represented as protocol events, including when the input cannot be decoded.

The compact LOAD summary is capped at 32 KiB of UTF-8 JSON. Post-envelope terminal Journal and SSE event measurements stay below 48 KiB, with the protocol's 1 MiB Worker frame and the Journal's 64 KiB data cap unchanged. The compatibility `metrics.buckets` coverage is exposed as a rolling 4,096-entry, one-second window; `LoadWindowMetrics` reports its own bin width and coverage. The compact result distinguishes execution outcome, performance verdict, detail completeness and archive availability. See [the full contract and compatibility note](load-terminal-result.md).

### Execution frame budget

Execution events have a shared limit of **1,048,576 UTF-8 bytes** per serialized JSON object, excluding the LF or CRLF delimiter. This counts encoded bytes, including JSON escaping, rather than Java UTF-16 characters. The Worker serializes through a bounded capture before writing stdout; it never writes a partial over-limit JSON frame. Ordinary events that exceed the budget retain bounded identifying/status/message fields and explicit `truncated` / `protocolLimit` metadata. The metadata reports only the known event type, measured original byte count and configured cap.

An oversized terminal `RESULT` retains the real status, exit code, execution ID, duration, up to four bounded original diagnostics, and final Worker metrics. Its result explicitly reports truncation. This legacy fallback keeps the prior non-LOAD result shape and remains available for older Workers. For an oversized legacy LOAD result, WorkerMain first projects a sanitized primary diagnostic from bounded failure diagnostics, metrics, preparation data, or outer diagnostics, preserving the real status and exit code; `ATT-WORKER-EVENT-TRUNCATED` is secondary. New Server-mediated LOAD output is projected before frame serialization, so normal detail volume does not use this fallback. The sanitized full legacy result is saved as `worker-protocol-result.json` in the assigned output directory for the normal archive publication policy; that policy may withhold oversized or otherwise disallowed entries. A failed detail-file write is reported as `detailsUnavailable` and does not replace the execution outcome. Typed preparation exceptions provide classification codes; classification does not parse exception-message substrings or fabricate failed counts. The existing result/report artifacts also remain subject to normal publication rules.

The Server independently drains oversized frames with bounded memory and records `ATT-SERVER-WORKER-EVENT-TOO-LARGE` with UTF-8 `sizeBytes`, `limitBytes` and an allowlisted header `eventType` (or `UNKNOWN`), without retaining payload content in diagnostics. A later valid result still completes the Job. If the Worker exits without a result, this protocol diagnostic remains the primary cause, with `ATT-SERVER-WORKER-EXITED` nested under `workerExit`, and is persisted with the terminal Job. Inspection daemon responses retain their separately configured aggregate response budget and fail on oversized responses rather than returning truncated discovery data.

## Process and output boundary

Run the packaged Worker with `java -cp 'lib/*' att.worker.WorkerMain`. Terminating that process cancels the job boundary. Engine resources use their normal cleanup paths during graceful termination; command-backed Tool processes receive best-effort cleanup. On Windows with Java 8, stopping a Worker does not guarantee that descendants of an external Tool process are stopped. This Worker contract does not add a mandatory native dependency solely to guarantee descendant cleanup; a future server may apply its own process supervision and escalation policy. Package-authored files are the caller's responsibility and are addressed only below `packageRoot` or an explicitly supplied output location.

The Worker artifact is shipped for future Server integration, but the supported end-user entry points remain `att.sh` and `att.bat`.
