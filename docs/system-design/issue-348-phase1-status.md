## Collection and revision behavior

For mixed Prometheus and business-call Jobs, after-drain calls run promptly after LOAD finishes. Their verified sidecars are available through the authorized Jobs API and Job Details tab as provisional, read-only evidence while the combined manifest remains `PENDING`; the manifest identifies `business: COMPLETE`, `prometheus: PENDING`, and the Prometheus `eligibleAt` deadline. The tab backs off its polls toward that deadline. Threshold evaluation and the combined verdict remain pending until the combined collection reaches a terminal state. Restart recovery resumes an unfinished Prometheus phase without repeating a completed business call. If the Server restarts during a `COLLECTING` business call, the collection fails closed with `SERVER_RESTART_INTERRUPTED`; the potentially side-effecting call is not retried.

The Settings starter SQL uses lowercase result labels, and its default Workload, Mix, and output mappings use those exact lowercase names. Mapping lookup is case-sensitive; users must align configured names with the result labels returned by their DBHelper or Package Tool.

Business-call execution uses the Package and Runtime Config revisions pinned at LOAD admission. If either revision changes before collection, the call does not run against current files. The sidecar records `NOT_EVALUATED` and a specific safe diagnostic. Executable source snapshots are not retained to run the admitted revision later.
