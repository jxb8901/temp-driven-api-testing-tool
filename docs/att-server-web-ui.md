# ATT Server Web UI

ATT Server bundles a static browser console at `<Tomcat context path>/ui/`, for example `https://host.example.com/tools/att/ui/`. Use a maintained Chrome, Edge, or Firefox release. With `server.auth.mode: container`, Tomcat protects `/ui/*` and `/api/v1/*`; HTTP Basic credentials are handled by the browser and are not stored by ATT. With `server.auth.mode: local`, ATT provides its login page and local account workflows. For authenticated deployments, use HTTPS.

## Local user management

In local mode, the current-user menu offers **Change password** to every signed-in local user. The form requires the current password, new password, and confirmation. A successful change revokes the current session and redirects to the login page with a success message. Password inputs stay in the active form only; the UI does not write them to local storage, session storage, URLs, or application logs.

Local `ADMIN` users can open **Settings → User Management** to search and sort the safe account list by login ID, display name, role, and status. They can create `ADMIN` or `USER` accounts, enable or disable an account, and reset a password. Create and password forms require matching confirmation and follow the Server's 12–1024 character password policy. Existing passwords are never displayed. Disabling a user or resetting a password requires confirmation and revokes that user's sessions. The Server prevents disabling the last active `ADMIN`, including concurrent disable requests. If every administrator is unable to sign in, use the offline recovery procedure in the [Server deployment guide](server-deployment.md#recover-a-locked-out-local-administrator); recovery only updates an existing `ADMIN` and never reopens bootstrap.

The account list and controls are available only to authenticated local `ADMIN` users. Other local users see no account data or management controls. In container mode, Settings explains that Tomcat or the configured SSO provider manages accounts; ATT does not show external accounts as if it owned them. Settings can use English or Traditional Chinese, follow the browser language, or save a language choice in this browser. The UI keeps the Server authoritative for access checks and password policy.

The console lists configured logical package IDs and recent persisted jobs. Select a package to submit Run, Debug, Load, or Validate requests, then open a job to follow progress, inspect terminal results and safe diagnostics, cancel an active job, or download logical artifacts. Inputs for package resources are logical paths relative to the selected package. The UI never accepts or displays `PACKAGE_ROOT` or Server storage paths. The Artifacts tab shows archive status, reports and bounded text previews from the verified ZIP. **Download Artifacts (.zip)** is the only download action; HTML reports open in an isolated viewer. See [artifact publication and recovery](reference/results-reports-evidence.md#att-server-job-artifact-publication). Direct job links such as `/ui/jobs/J10045` redirect to the canonical hash route, which reloads the job from the public API and SSE.

The Package Resource Explorer lists configured Cases, Templates, Flows, and Tools by package-scoped logical resource ID. It supports type and text filters, stable server-side sorting across all matching resources before pagination, encrypted cursors, resource details, and safe references. Under the default `safe-package-files` policy, eligible package-local Tool scripts and safe `&{...}` targets can be opened without per-file entries when reached from an authorized source; Template and Flow YAML remains a sanitized projection. `allowlist-only` uses exact package-relative `server.inspection.safeTextSources` entries. External scripts require an exact canonical per-package allowlist under a configured external root, and their filesystem paths are hidden. Case details show identity and stage/template metadata but hide workbook business values. Reverse references include at most 100 inline entries plus an exact count and `referencedByHasMore` flag. The Explorer does not browse arbitrary files, execute Tools, or modify package content. If a package changes during pagination, or the sort/filter query changes, the Server rejects the stale cursor and the UI can refresh the list.

Debug is available from a selected Template, Flow, or Tool detail. The form loads safe defaults from the target's optional `debug.yaml`; if it is missing, the Server supplies valid empty `att-debug/v1.2` defaults. Package-authored values are hidden by default. A `$attDebugKeepDefault` marker retains a hidden value when left unchanged; replace it with an explicit value to override it. Edit nested values as JSON objects, reset to the loaded defaults, validate, and review the redacted YAML preview before starting Debug. All targets use `inputs`; Template and Flow also use `vars`, while Tool uses `arguments` and does not accept `vars`. The Server binds each in-memory draft to the authenticated Principal and current package revision. Drafts expire after 10 minutes and are invalidated by a Server restart. Editing or submission never writes a package file. The original path-based Debug API remains available to compatible clients.

Browser-created Quick and Advanced Load are disabled by default. A Server administrator must set `server.inlineLoad.enabled: true` and configure server-owned workload, target, user, rate, concurrency, and duration caps before those forms can create drafts. The UI reads `inlineLoadEnabled` from `/api/v1/version` and disables the Advanced Load entry and hides Quick Load when the feature is off; direct navigation displays the disabled state. A disabled endpoint returns `403 ATT-SERVER-INLINE-LOAD-DISABLED`; an over-limit draft returns `400 ATT-SERVER-INLINE-LOAD-LIMIT` with a summary naming the exceeded setting. This switch does not disable existing path-based Load clients.

Quick Load is a first-level route for one selected Template, Flow, or Tool. Its bounded template picker includes compatible policy-only YAML files from the package `load/` directory, including `load/load.visualuser.yaml` and `load/load.arrivalrate.yaml` when compatible, plus the bundled **Quick smoke** preset for Virtual Users. Selecting a template loads its supported settings; when no compatible package template is selected, the Server supplies the model-specific defaults or a bundled 10-second low-intensity fallback. Preset and model changes update the unsent scenario; the target remains fixed, and Debug-local Testdata imports are never promoted implicitly. Advanced Settings retain thresholds, evidence, execution options, Testdata paths, and a complete scenario preview. Validate the single-target scenario and confirm before submitting traffic. The Server binds the draft to the authenticated Principal and current package revision and submits the same immutable scenario it validated. Schedule carries that validated draft into an immutable inline Load snapshot, so the target, environment, inputs, pacing, thresholds, and evidence do not need to be re-entered.

Advanced Load is available from each package on the home page. Choose `virtualUsers` or `arrivalRate` before adding workloads; the selected model applies to every workload. Set a shared timing envelope, optional seed, package-relative Testdata imports, execution defaults, aggregate thresholds, and evidence policy. Add, duplicate, reorder, or remove workloads. Each workload has its own intensity, target, Testdata policy, and thresholds. A workload uses one Template, Flow, or Tool target, or a weighted target mix for Virtual Users. Arrival Rate workloads use one target each. Target sidecar defaults contain only safe business fields; Debug `case`, `stage`, and local Testdata are not copied. Validate the full scenario, review the safe YAML, then confirm before the Server submits its immutable draft through the normal Load scheduler. Copy and export are available only when the preview is not redacted.

Schedules is available in the React console at `#/schedules` when `/api/v1/version` reports `loadSchedulingEnabled: true` and the caller has operational access. Every active local `USER` or authenticated container principal in `server.authorization.userRole` can manage the shared schedules; `ADMIN` accounts receive system and account administration only. Schedule creator identity is retained for audit and display, not as an access boundary. Create schedules from a validated Quick or Advanced Load draft, or use an existing package-relative Load scenario. Draft-based schedules retain the Server-normalized immutable scenario snapshot; their API view exposes `inlineSnapshot` without returning the scenario contents. The Server revalidates the saved snapshot and package revision before each occurrence. The page supports optional descriptions and tags, next-run previews in the selected IANA timezone, and daily, weekly, or five-field cron recurrence. Preview calculates occurrence times only; saving validates the complete scenario and target closure through the inspection Worker. Switching recurrence replaces the stored trigger, while editing only metadata keeps that trigger and its Server-confirmed next run, so a consumed one-time schedule can still be renamed or re-described. A save-validation error shows its code and available summary, field, source location, package, environment, target, and suggestion, plus the request ID. Use **Review field** to focus the matching control or open the saved snapshot. Host-local absolute paths are masked. New schedules remain paused unless you select **Enable after saving**. Run Now and delete require confirmation. Occurrence history explains skips and submission failures and links submitted runs to the normal job page, results, events, and artifacts. Schedule state and history survive Server restarts. Editing or deleting a schedule does not cancel an accepted job.

From Quick or Advanced Load, **Schedule…** opens the schedule form over the current editor and shows the safe validated preview. Cancel returns to that same draft. The Server rejects an inline snapshot containing credentials or other classified sensitive values before saving the schedule; keep such values in package-managed configuration.

The shared React shell follows the operating system's light or dark preference until you choose a theme; your choice is saved in browser storage. Press `/` or `Ctrl K`/`⌘ K` to search pages, `?` to open the shortcut list, and `Esc` to close a dialog or mobile navigation. On the Advanced Load page, `Ctrl Enter`/`⌘ Enter` starts a live, validated draft only after the existing confirmation. The shell and Schedules editor adapt at tablet and phone widths, keep keyboard focus visible, respect reduced-motion settings, and use text labels alongside status colors.

The first-level Configuration workspace at `#/configuration` opens without a Package, including with **All packages** selected. Source, Declared, Effective and Compare use the centrally managed Runtime configuration and global authenticated Configuration API; Environment changes effective values, not the source tree. There is no Package fallback. Testdata alone has its own Package selector and resolves records only inside that Package. Older `#/configuration/{packageId}` links remain supported, but shared views ignore that Package context. Bounded file traversal, source-reference authorization, source policy, masking and admin-field controls remain enforced. Invalid or unavailable shared configuration is shown explicitly. See [Shared Configuration](reference/configuration.md#shared-configuration-in-studio).

Declared and Engine-effective views use the shared runtime `FrameworkConfigLoader` selection rules and make no DB, MQ, HTTP, or SSH connections. Root-only packages can inspect their configured default without selecting a profile. Compare defaults to environment-specific values and filters the selected section before pagination; **Include inherited/global fields** opts into shared values and their provenance. Configuration administrators can also request additional non-secret DB properties and evidence fields with **Show additional DB configuration fields**. Container-auth deployments use `server.inspection.configurationAdminRole` (default `ATT_ADMIN`); local-auth deployments require a local `ADMIN`. Credentials and configured sensitive values remain hidden. Values classified as hidden remain distinct from missing values and are never compared by the UI. Tool details link to their configuration section. Public endpoints and paging parameters are documented in [ATT Server deployment and API](server-deployment.md#package-configuration-inspection).

Source and preview panes share a lazy-loaded CodeMirror editor for YAML, JSON, XML, SQL, Shell, and plain text. It decorates ATT's `${...}`, `#{...}`, `@{...}`, and `&{...}` expressions. Only file references carrying an opaque Server-issued token become links back to Configuration. The Server binds each token to the package, origin, and target, then rechecks the reference before returning text; the UI does not build links from client-parsed paths. The editor provides copy, find, go-to-line, fullscreen, and safe formatting actions; it does not execute code. Debug sidecar scalar controls remain form-first, with Advanced JSON for nested values. Threshold and Evidence use form controls with Advanced JSON; invalid JSON remains in the draft and cannot replace the last valid configuration.

Open **Schedules** to see persisted RUN and LOAD definitions first. Search by name, target, package, environment, creator or cron; filter by execution type, state, package and available creator identities. The list shows each definition's type, target, package/environment, timezone, recurrence, next run and state. Creator is informational and does not limit which active USER can manage a schedule. It does not fetch job history until you select **History**. Creator and recent-status fields appear only when supplied by the authorized API response.

Select **New Schedule** (`#/schedules/new`) or **Edit** (`#/schedules/<id>/edit`) to open a separate form. For RUN, validate a Case, Template, Flow, Tool or typed batch selection in **Run**, then choose **Schedule…** from Review. Validated Quick/Advanced/YAML LOAD drafts use the same schedule drawer. The drawer retains the source editor and passes its server-issued draft ID unchanged, preserving typed inputs, selected Cases, Debug mode and LOAD policies. Saving creates a definition without executing it. New schedules default to paused; review the next-occurrences preview before enabling execution. You can also create a LOAD schedule from an existing package-relative scenario path.

**Cancel** and **Back to Schedules** protect unsaved changes. Reloading or closing a tab prompts when a schedule form is dirty; switching tabs keeps the in-memory form. Drafts and credentials are never written to browser storage. A refresh cannot restore an unsaved validated draft: return to its source and validate again. Edit and History deep links reload saved definitions from the Server. Legacy `#/load-schedules` and `#/scheduled-load` links still open Schedules.

**History** opens `#/schedules/<id>/history`; individual occurrences link to `#/schedules/<id>/history/<occurrenceId>`. The view covers the latest 100 retained occurrences and identifies unavailable older records. Job links appear only when the Server provides an available job status; job/report permissions are rechecked by the Jobs API. **Run Now**, **Pause/Resume**, and **Delete** require confirmation. A manually triggered LOAD definition remains LOAD. Existing Scheduled Debug definitions appear as RUN with Debug mode and retain their legacy backend identity through the compatibility adapter. Misfire, retention, capacity, revision checks and DST remain governed by the existing unified Scheduler; this UI does not introduce another scheduler.

## Use the React Explorer and Debug form

The React Explorer presents package resources, the selected definition, and resource actions in a three-pane workspace. Select a Case, Template, Flow, or Tool to open its details. The `#/packages/{packageId}/resources/{type}/{resourceId}` hash route restores the selected resource on reload and supports browser navigation. The Definition, Source, and Dependencies tabs support keyboard navigation with the arrow keys, Home, and End.

The Source tab loads only the Server's safe source projection. It displays at most the first 200,000 characters and 12,000 lines, virtualizes visible lines, and renders source as text. Refresh it after a package change. **Copy displayed source** copies only the text shown within those limits. An empty or unavailable projection is reported explicitly; authentication and permission errors do not include raw response details.

Debug and case execution are available from the resource inspector. Sidecar-provided scalar leaves have typed controls for text, numbers, booleans, and null. Nested values and the complete business input remain editable in **Advanced JSON**. Correct invalid JSON or scalar values before validating. **Reset defaults** restores the values loaded from the sidecar. If the Server marks a sidecar value redacted, the form shows a keep-default marker; it does not reveal the hidden value. Leave the marker selected to preserve the package value, or choose a type and enter an explicit override. Validate and inspect the safe preview before starting Debug. The Server remains authoritative for validation and access checks.

Changing package, resource, or environment while Debug edits are unsaved asks before discarding them. The same guard covers hash-route navigation and browser back/forward changes. The optional job label is sent with the execution request as its Principal label; it does not replace Tomcat authentication. If the session expires, sign in again and retry. Anonymous deployments can still use the label when the Server permits the request.

## React Load builder and Jobs/Results

The Advanced Load route uses typed controls for duration units, Virtual Users, Arrival Rate, maximum concurrency, and think time. Target sidecar defaults use typed scalar controls for `inputs`, `vars`, and Tool `arguments`; nested values remain in Advanced JSON. Model-specific constraints are reflected in the form, while the Server remains authoritative for validation, policy limits, draft expiry, package revision, and execution. The UI reviews and submits the same Server-issued draft after confirmation, and only offers preview copy/export when the response is not redacted.

The Jobs route loads the latest rows returned by the Server (at most 100). Status, package, type, created-date filters, sorting, and client-side paging operate only on those loaded rows; principal search is sent to the Server. The API does not return an environment field for these rows, so the UI does not offer an environment filter. Refresh keeps the selected filters and sort while the response is pending. Job detail has stable Overview, Live logs, Events, Results, Artifacts, and Metrics tabs. Native same-origin `EventSource` reconnects with the browser's `Last-Event-ID`; cancellation requires confirmation and the UI waits for Server status events. Metrics show only values returned by the job and result endpoints: Server timing and Worker JVM data remain separate from Load result metrics, and no throughput chart is inferred when the result has no time-series buckets.

The Explorer is a React and TypeScript single-page UI built with Vite during the `att-web` Maven resource phase. Maven copies the generated static assets into `META-INF/resources/ui/`; the Server WAR packages those assets for Tomcat. Node.js is a build-time tool only. The deployed UI calls the same-origin public REST API and does not require a separate Node process or frontend service.

The browser uses only the public same-origin `/api/v1` REST and SSE contract. REST requests and native `EventSource` use the browser's container-managed authentication. SSE reconnects use the browser's standard `Last-Event-ID` behavior; refreshing a job view reloads job state and retained events from the Server. Closing the browser tab does not cancel the job. Cancellation requires confirmation and the UI waits for the Server's terminal status.

The UI checks the Server API version before loading job data. Terminal SSE results close the browser event stream rather than reconnecting to completed jobs; live progress is shown separately from bounded event history. The authenticated static UI and API share one Tomcat security boundary.

The console is delivered as static `att-web` JAR resources under `META-INF/resources/ui/` and packaged in the Server WAR. Relative URLs support non-root Tomcat context paths without a separate frontend service or runtime Node.js dependency. The Server applies a same-origin content security policy and rejects state-changing browser requests with an unexpected `Origin`; no credentialed CORS policy is needed. Browser-rendered API text is inserted as text, and the event list is bounded to 500 entries.

For fields without a public discovery schema, the UI uses safe sidecar data for typed scalar controls and provides Advanced JSON for nested values. Server validation remains authoritative; browser-side validation and filtering are not authorization boundaries.
