# Worker and output lifecycle performance investigation

This investigation starts from PR #282, commit `c6cd39e511dacc6feae480293fd453b4f0d7994d`, with ATT 4.2.3. Measurements below are synthetic local evidence, not production throughput claims. The implementation branch is `feature/issues-278-281-performance`.

## Environment and reproduction

The first measurements used macOS on arm64, Homebrew OpenJDK 26.0.1 and Maven 3.9.16. Hardware CPU model and physical memory were unavailable to the sandbox. Fixtures use no external SUT or credentials. The existing Java 8 compiler targets remain unchanged.

Run the focused regression suite from the repository root:

```sh
mvn -B -ntp -pl att-server -am test \
  -Dtest=ArtifactInventoryTest,ArtifactArchiveTest,DbHelperExecutorTest \
  -Dsurefire.failIfNoSpecifiedTests=false \
  -Dskip.npm=true -Dskip.installnodenpm=true -Datt.skipFrontendUnitTests=true
```

Frontend skipping here isolates backend tests. It is not evidence for the release or browser gates.

## DB connection occupancy (#279)

The baseline fixture uses the existing synthetic JDBC driver, a real run-scoped Hikari pool with maximum size 1 and a 250 ms acquisition timeout. It performs a query, attempts an independent borrow during the non-DB tail, performs an update and finalizes the Case. Four combinations cover `statement|case` and `commit|rollback`.

Before production changes, both statement configurations retained one active connection after the completed query. The independent borrow timed out in all four combinations. Baseline query durations were 126.785 ms for the first cold query, then 0.624, 0.689 and 0.958 ms. The cold sample includes first-use initialization. These four observations are not a latency distribution or a production benchmark.

With early return, both statement configurations have zero active connections immediately after the statement. The independent borrow succeeds, and the later update safely reacquires. The Case configurations retain their connection and still produce the expected acquisition timeout. Their shared transaction and final commit/rollback evidence remain intact. Finalization states remain `AUTO_COMMITTED`, `ROLLED_BACK`, `COMMITTED` and `ROLLED_BACK`, respectively.

The cancellation regression blocks an in-flight JDBC `cancel()` call while the query returns. It verifies that the connection stays borrowed until cancellation completes, the operation reports `TIMEOUT`, and exactly one handle is released. SQL errors for query and update also release the statement connection and allow the next action to borrow. Repeated abort does not return the same handle twice.

Additional regressions interleave two DBHelpers with different transaction scopes in one Case, verify that statement scope re-borrows while case scope retains one independent transaction, and prove run shutdown finalizes and closes an active Case connection exactly once. An executor-level pool exhaustion test verifies `DB_POOL_TIMEOUT`, sanitized diagnostics without SQL, JDBC URL or credentials, timeout/statement metrics, and successful recovery after the held connection is returned. The English and Traditional Chinese DBHelper references describe the same release boundary, metric names and sanitized timeout classification.

The current change applies only to provider-backed statement connections. Direct RUN/DEBUG connection ownership and the default `case/rollback` policy remain unchanged. Aggregate hold/statement telemetry is bounded by helper count; it includes no query data.

The opt-in `DbOccupancyPerformanceBenchmark` runs the real `DbHelperExecutor` against H2 through Hikari, with 250 arrivals at 55/s, a 20 ms non-DB tail between `SELECT 1` and a unique insert, and 1- or 4-connection warm pools. It covers both scopes and both finalization policies. The same harness ran on master `52b319ac` and feature `05683a0c` on this Mac arm64/OpenJDK 26.0.1 host. No SUT or credentials are used. The single run delivered these results for the one-connection pool:

| Scope / end | Master throughput | Feature throughput | Master / feature case p95 | Master / feature acquire-wait p95 | Master / feature connection-hold p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| statement / commit | 36.5 /s | 54.9 /s | 2,211.87 / 39.89 ms | 430.72 / 0.17 ms | 32.01 / 0.92 ms |
| statement / rollback | 38.8 /s | 54.9 /s | 1,818.10 / 37.08 ms | 408.87 / 0.02 ms | 31.01 / 0.58 ms |
| case / commit | 39.0 /s | 38.4 /s | 1,783.67 / 1,899.62 ms | 409.71 / 409.94 ms | 30.78 / 30.84 ms |
| case / rollback | 38.5 /s | 39.4 /s | 1,875.67 / 1,734.34 ms | 410.83 / 399.85 ms | 30.70 / 30.69 ms |

With statement scope, returning the connection between DB actions lets the 1-connection pool sustain the offered arrival rate and removes the queue seen on master. Case scope continues to hold its transaction across the non-DB tail, as required. The 4-connection scenarios are near the offered rate on both revisions. Every scenario completed all 250 cases with zero DB pool timeouts; commit fixtures contained 250 rows and rollback fixtures contained none. These are one-run synthetic results, not production throughput claims or multi-run confidence intervals. Full raw reports are `baselines/issues-278-281/db-occupancy-master.json` and `db-occupancy-feature.json`.

Reproduce on either revision with `mvn -pl att-server -am -Dtest=DbOccupancyPerformanceBenchmark -Dsurefire.failIfNoSpecifiedTests=false -Datt.server.benchmark.dbOccupancy=true -Datt.server.benchmark.dbOccupancy.output=/tmp/db-occupancy.json -Datt.benchmark.commit=<tested-sha> test`. The full reactor also rebuilds the web UI and runs its 301 typed component tests.

## Historical archive inventory (#280 P1)

The fixture creates 100,002 `.id` files and two report-shaped private JSON files under sibling `load/<run>/.exec-id-reservations` directories, plus one eligible report. Baseline publication failed with `Artifact inventory exceeds limits` after 614.896 ms. This excludes fixture creation and deletion.

The bounded visitor prunes only that exact three-component private namespace before counting candidates. It does not follow symlinks. Uppercase aliases and links remain untrusted candidates. Root and other directories still count toward the 50,000 candidate cap. The 64-level depth, approved entry, sanitized byte, manifest/digest/CRC, verification/fsync and atomic publication contracts remain in effect. Internal reservation files do not create omissions or mark an otherwise complete archive incomplete.

The same fixture published successfully in 169.258 ms after the change, with exactly one manifest entry and no omissions. These single measurements establish the failure/recovery behavior; they do not establish a general performance ratio. All 16 existing archive regressions and the three new inventory regressions passed at this checkpoint.

## Prototype checkpoint and open compatibility questions

Raw measurements are retained under `baselines/issues-278-281/`. The original five-sample cold DEBUG report used the JVM default heap; the later controlled cold report uses the same 256 MiB heap cap as prewarming. Do not compare the original cold report to the warm report as a controlled speedup. Early DEBUG reports observe terminal status before cleanup and can omit teardown timings; the harness now waits for durable termination timing, so those reports must be refreshed for the final comparison.

The prewarm prototype scrubs application environment from idle native processes. Assignment installs a bounded immutable environment in framework configuration resolution and child-Tool launches. Direct `System.getenv()` calls inside third-party Java code do not use that overlay, so effective DB/MQ/SSH/HTTP helpers, discovery failures and additional Worker library directories require cold dispatch. A fresh internal Inspector capability binds eligibility to the package revision, and the assigned Worker independently verifies both before business execution. JVM startup options and font bootstrap overrides also require cold dispatch. See the EN/ZH `docs/system-design/execution-prewarm` documents for the precise current eligibility and configuration contract.

The fallback integration exposed a Debug draft freshness gap: validation could read current configuration while returning a cached index revision before a delayed filesystem watcher event arrived. Debug draft validation now rebuilds source identity before validation and verifies it again afterward; submission independently rejects a stale revision before admission. Existing read-only form/index caching remains. This adds measured work at trust boundaries and must be included in final before/after latency comparisons.

`debug-prewarm-eligibility-fallback.json` retains five real short DEBUG samples (four warm, one no-ready cold fallback), followed by an additional native-resource cold fallback that completed PASS. Eligibility took 9.28–16.16 ms in those five samples; first meaningful events were 357.60–395.69 ms for warm samples and 614.93 ms for the cold sample. The small sample count is protocol/compatibility evidence, not a p95 or throughput conclusion. The report includes durable termination timing. The additional native-resource Job exposes fixed reason `native_resource_environment`; no driver connection is opened by eligibility. Unit coverage also switches environments and rejects source changes and missing revisions before warm business execution.

Pool and protocol tests cover readiness, one request, multiple-document rejection, LOAD rejection, package affinity, registry mismatch, child-Tool environment, runtime metadata changes, failed handshake backoff, dead-idle replacement, transferred lease ownership, restart descendant cleanup, uncertain-fence recovery markers and shutdown. The Tomcat 11 redeploy CI test now passes for Server compactor/JDBC cleanup, but does not enable the prewarm pool. Job-level cancellation/timeout, kill-during-dispatch, durable Job quarantine and enabled-pool WAR undeploy coverage remain open. Idle RSS measurement and comparison under 1/2/4 concurrent requests remain pending. The feature remains disabled by default; this checkpoint is not a release or completion claim.

The expanded baseline and read-path prototype ran on the same Mac OS X 26.1 arm64 host with OpenJDK 26.0.1, eight reported processors, and a 2 GiB max heap. The baseline production `JobStore.java` matched master `52b319ac`; baseline and candidate each used 256 samples and 10 warmups. At 16 clients, median per-thread mixed-cycle p95 fell from 44.83 ms to 29.69 ms, measured throughput rose from 535 to 823 cycles/s, direct job-list p95 fell from 24.45 ms to 0.99 ms, and monitor blocking fell from 7.12 s to 4.41 s per thread. However, synchronized auth-user lookup p95 rose from 0.045 ms to 14.90 ms and sampled peak heap rose from 202 MB to 527 MB; H2 file-footprint growth was similar at about 638 MB. The reader overlap moves latency and memory pressure onto other control-plane operations. **No-go:** keep the production list methods synchronized until a full HTTP workload plus RSS and physical-I/O measurements show that the trade-off is acceptable. The raw baseline is `baselines/issues-278-281/control-plane-feature-e047c770.json`; the measured prototype is `baselines/issues-278-281/control-plane-feature-6d329edd.json`.

Across the same reports, 1,000-case RUN-definition parsing measured p95 0.233/0.238 ms and 50-JAR classpath enumeration measured p95 0.457/0.572 ms for baseline/prototype; these do not justify a cache. At 1,000 target events/s, the slow synthetic observer reduced achieved append rate to about 322/s and raised append p95 to 3.3 ms, while none/fast/throwing observers sustained about 1,000/s with sub-millisecond p95. The production SSE listener only performs a bounded queue offer, so this synthetic slow callback does not justify changing journal durability or observer ordering. No journal production change is proposed.

## Archive staging decision (#280 P2)

The hot path is sanitized export materialization, reread and deletion, after Publisher approval but before/after ZIP writing. The original disk-only pipeline took 1,673 ms p50 for 2,049 files, including 118 ms p50 cleanup. Publisher redaction alone took 872 ms p50, so staging optimization cannot remove most work. **Go:** cap retained sanitized snapshots at 8 MiB per writer and spill excess to the existing disk path. The semantic risk is changing approval/HTML snapshot behavior; preserve one Publisher call per entry, do not reread raw output, and prove equality of final bytes between the two paths. Do not introduce unbounded full-archive buffering or remove verification/fsync.

The explicit harness uses seed 280, 2 warmups and 20 samples per fixture, the same machine/JDK and identical fixture-body hashes. Fixtures have 24 or 2,048 generated text files across four workload directories plus one linked HTML report. Synthetic secret-like fields are redacted; generated bodies are deterministic Base64 noise. Timings exclude fixture generation and the benchmark's additional correctness reads. No SUT is contacted.

| Fixture | Disk-only p50 / p95 ms | Capped staging p50 / p95 ms | Temporary exports, disk → capped |
| --- | --- | --- | --- |
| 25 files | 22.82 / 29.57 | 16.94 / 21.33 | 25 → 0 |
| 2,049 files | 1,673.04 / 1,810.23 | 1,371.52 / 1,419.14 | 2,049 → 521 |

For the large fixture, the capped run retained at most 8,387,874 sanitized bytes and spilled 2,861,853 bytes. Cleanup p50 fell to 25.96 ms; Publisher p50 remained 883.27 ms. These are local synthetic measurements, not arrival-throughput or production speedup claims.
